## 1. Why C++ Owns Game Dev

Game development demands:
- **Predictable performance**: 60 FPS = 16.6 ms per frame. No GC pauses, no JIT warmup.
- **Manual memory control**: pool allocators, arena allocators, cache-friendly layouts.
- **Hardware access**: direct interaction with GPU, audio, input devices.
- **Cross-platform**: a game ships to Windows, Mac, Linux, PS5, Xbox, Switch, mobile.
- **Mature tooling**: decades of debuggers, profilers, engines, middleware.

C++ checks all boxes. The alternatives:
- **Rust** — gaining ground; safer memory model, but smaller ecosystem.
- **C#** (via Unity) — popular for indies, mobile, AA. Slower than C++ in worst case.
- **GDScript** (Godot) — for indies, scripting.

In AAA: still C++. In indie: split between C++ (Unreal/custom), C# (Unity), and emerging Rust.

## 2. The Major Engines

### Unreal Engine 5
The de facto AAA engine. C++ + Blueprints (visual scripting).
- Used by: Fortnite, Senua's Saga, Black Myth: Wukong, Cyberpunk's sequel, many AAA titles.
- Strengths: graphics tech (Nanite, Lumen), rendering, networking, cross-platform.
- Weaknesses: heavy, long compile times, opinionated patterns.
- License: royalty-based (free until $1M revenue per game).

### Unity
The most popular engine by user count. C# scripting, C++ engine internals.
- Used by: most mobile games, indies, many AA.
- Strengths: accessibility, asset store, mobile pipeline.
- Weaknesses: graphics behind Unreal, recent business missteps eroded trust.

### Godot
Open-source. C++ engine, GDScript (Python-like) or C# scripting.
- Used by: indies, hobby projects.
- Strengths: free, lightweight, growing fast.
- Weaknesses: 3D capabilities behind Unreal.

### Custom engines
AAA studios often build their own:
- **id Tech** — Doom Eternal.
- **Frostbite** — EA.
- **Decima** — Guerrilla Games (Horizon).
- **Snowdrop**, **Anvil**, **Northlight**, **REDengine**, etc.

Smaller teams use **bgfx**, **The Forge**, **Filament** (rendering libraries on top of which you build).

### Frameworks (not full engines)
- **SDL** — windowing, input, audio.
- **SFML** — similar, more C++-idiomatic.
- **raylib** — beginner-friendly.

For learning or simple games.

## 3. Unreal Engine

The most relevant engine for serious C++ game dev.

### Architecture
- **Engine core**: C++ classes (`UObject`, `AActor`, `UComponent`).
- **Reflection**: macros like `UCLASS()`, `UPROPERTY()`, `UFUNCTION()` generate code for serialization, garbage collection, editor integration.
- **Blueprints**: visual scripting layered on C++.
- **GAS** (Gameplay Ability System): for abilities, status effects, scaling.
- **Slate** / UMG: UI.

### Hello world Unreal class
```cpp
// MyActor.h
#pragma once

#include "CoreMinimal.h"
#include "GameFramework/Actor.h"
#include "MyActor.generated.h"    // generated by Unreal Header Tool

UCLASS()
class MYGAME_API AMyActor : public AActor
{
    GENERATED_BODY()
    
public:
    AMyActor();
    
    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Stats")
    float Health = 100.0f;
    
    UFUNCTION(BlueprintCallable, Category = "Combat")
    void TakeDamage(float Amount);
    
protected:
    virtual void BeginPlay() override;
    virtual void Tick(float DeltaTime) override;
};
```

```cpp
// MyActor.cpp
#include "MyActor.h"

AMyActor::AMyActor()
{
    PrimaryActorTick.bCanEverTick = true;
}

void AMyActor::BeginPlay()
{
    Super::BeginPlay();
}

void AMyActor::Tick(float DeltaTime)
{
    Super::Tick(DeltaTime);
}

void AMyActor::TakeDamage(float Amount)
{
    Health -= Amount;
    if (Health <= 0)
    {
        Destroy();
    }
}
```

### Unreal's macro system
- `UCLASS()` — marks an Unreal class.
- `UPROPERTY()` — registers a field with the reflection system.
- `UFUNCTION()` — exposes a function (to Blueprint, RPC, etc.).
- `GENERATED_BODY()` — placeholder for generated code.

The Unreal Header Tool (UHT) pre-processes these and generates `.generated.h` files.

### Strings: `FString`, `FName`, `FText`
- `FString` — mutable string, like `std::string`.
- `FName` — interned, fast comparison (for IDs, asset names).
- `FText` — localized text.

```cpp
FString Name = TEXT("Alice");
FName Tag = TEXT("Player");
```

### Containers: `TArray`, `TMap`, `TSet`
Unreal's STL equivalents:
```cpp
TArray<AActor*> Enemies;
TMap<FName, int32> Scores;
TSet<int32> UniqueIds;
```

Same role as `std::vector`, `std::unordered_map`, `std::unordered_set`. Different API.

### Smart pointers: `TSharedPtr`, `TWeakPtr`, `TObjectPtr`
- `TSharedPtr<T>` — reference-counted (for non-UObject types).
- `TUniquePtr<T>` — unique ownership.
- `TObjectPtr<T>` — for UObject; supports the Unreal GC.

`UObject` instances are garbage-collected. Hold them via `UPROPERTY()`-marked fields or `TStrongObjectPtr`/`TWeakObjectPtr`.

### Modules and the build system
Unreal projects organize into modules. Each module has a `Build.cs`:
```csharp
public class MyGame : ModuleRules
{
    public MyGame(ReadOnlyTargetRules Target) : base(Target)
    {
        PCHUsage = PCHUsageMode.UseExplicitOrSharedPCHs;
        PublicDependencyModuleNames.AddRange(new string[] { 
            "Core", "CoreUObject", "Engine", "InputCore" 
        });
    }
}
```

### Learning Unreal
- Official docs: docs.unrealengine.com.
- "Unreal Engine 5 C++ Developer" courses on Udemy / Coursera.
- The "Lyra" sample project.
- Tom Looman's tutorials.

## 4. Game Loop Fundamentals

The heart of any game:

```cpp
void run() {
    while (running) {
        process_input();
        update(delta_time);
        render();
    }
}
```

### Variable vs fixed timestep
- **Variable timestep**: update with whatever `delta_time` is. Easy but can cause physics issues at low FPS.
- **Fixed timestep**: update at fixed intervals (e.g., 60 Hz). Render at variable rate. Stable physics.

The classic "Fix Your Timestep" article (Glenn Fiedler):
```cpp
double accumulator = 0;
const double dt = 1.0 / 60.0;

while (running) {
    double frame_time = get_frame_time();
    accumulator += frame_time;
    
    while (accumulator >= dt) {
        update(dt);
        accumulator -= dt;
    }
    
    double alpha = accumulator / dt;
    render(alpha);    // interpolate state for smooth rendering
}
```

### Frame rate
Target frame times:
- 60 FPS = 16.67 ms.
- 30 FPS = 33.3 ms.
- 120 FPS = 8.3 ms.
- 144 FPS = 6.9 ms.

Anything taking longer than your target frame time drops a frame.

### Profiling
Game-specific tools:
- **Visual Studio Profiler**.
- **Tracy** — lightweight, real-time C++ profiler.
- **Optick** — game-focused.
- **PIX** (Windows) — GPU profiling.
- **NSight** (NVIDIA).
- **RenderDoc** — frame debugging.

Profile early, profile often. "Premature optimization is the root of all evil" applies less here — game code is performance code.

## 5. Entity-Component-System (ECS)

A data-oriented architecture pattern. Replaces OO inheritance for game objects.

### Traditional OO
```cpp
class GameObject {
    virtual void update();
};

class Tank : public GameObject {
    void update() override;
};

class Tree : public GameObject {
    void update() override;
};
```

Problems:
- Multiple inheritance / interface explosion.
- Cache-unfriendly (each object is a separate allocation).
- Hard to compose behaviors dynamically.

### ECS
- **Entities** — IDs (just an integer).
- **Components** — pure data, stored in arrays per type.
- **Systems** — logic that operates on entities with specific component combinations.

```cpp
struct Position { float x, y, z; };
struct Velocity { float vx, vy, vz; };
struct Health { int hp; };

// Storage:
std::vector<Position> positions;       // for each entity that has Position
std::vector<Velocity> velocities;       // for each entity that has Velocity
std::vector<Health> healths;             // ...

// A system:
void movement_system(float dt) {
    for (size_t i = 0; i < entity_count; ++i) {
        if (has_components(i, Position, Velocity)) {
            positions[i].x += velocities[i].vx * dt;
            positions[i].y += velocities[i].vy * dt;
            positions[i].z += velocities[i].vz * dt;
        }
    }
}
```

(Real implementations use bitmasks or sparse sets to track which entities have which components.)

### Benefits
- **Cache friendly**: all positions in one contiguous array — fast iteration.
- **Composable**: a "Player" entity has Position + Velocity + Input + Health + Renderable. A "Bullet" has Position + Velocity + Damage. Mix and match.
- **Data oriented**: thinking about "what data is processed together" instead of "what objects exist."

### ECS libraries
- **EnTT** (C++17/20) — popular header-only.
- **flecs** — full-featured.
- **entt** in Unreal — via plugins.
- **Bevy's ECS** — Rust, but worth studying.

### EnTT example
```cpp
#include <entt/entt.hpp>

entt::registry registry;

// Create entity with components
auto entity = registry.create();
registry.emplace<Position>(entity, 0.0f, 0.0f, 0.0f);
registry.emplace<Velocity>(entity, 1.0f, 0.0f, 0.0f);

// System
auto view = registry.view<Position, Velocity>();
for (auto entity : view) {
    auto& pos = view.get<Position>(entity);
    auto& vel = view.get<Velocity>(entity);
    pos.x += vel.vx * dt;
}
```

Clean, fast, modern.

### When ECS, when not
- Many entities with varied composition → ECS.
- Few distinct entity types → OO might be simpler.
- ECS has overhead conceptually; some game devs find pure data-oriented design overkill for simple games.

Big engines use ECS or "data-oriented" variants. Unity has DOTS (Data-Oriented Tech Stack). Unreal has Mass Entity.

## 6. Graphics APIs Overview

Game rendering goes through a graphics API to talk to the GPU.

### The major APIs
- **OpenGL** — old, simple, widely supported. Deprecated on macOS, not on Vulkan-compatible mobile.
- **Vulkan** — modern, low-level, explicit. Steep learning curve.
- **DirectX 12** — Microsoft's modern API. Windows + Xbox.
- **Metal** — Apple's API. macOS + iOS.
- **WebGPU** — for browsers; getting traction outside too.

Engines abstract over these — write to the engine, the engine targets each API.

### Modern vs old APIs
- **Old (OpenGL, DX11)**: implicit, simpler. Driver hides complexity.
- **New (Vulkan, DX12, Metal)**: explicit. You manage memory, command buffers, synchronization. More performant but harder.

For learning: start with OpenGL or DX11. For modern engine work: Vulkan or DX12.

### Cross-platform abstractions
- **bgfx** — supports many backends.
- **The Forge** — used in production AAA.
- **Diligent Engine**.
- **SDL_GPU** (new).

### Shading languages
- **GLSL** — OpenGL/Vulkan.
- **HLSL** — DirectX.
- **MSL** — Metal.
- **WGSL** — WebGPU.

You write shaders in one of these; they're compiled to GPU bytecode.

## 7. OpenGL Basics

OpenGL is old but accessible. Good for learning graphics fundamentals.

### Setup (with GLFW for windowing + GLAD for loading)
```cpp
#include <GLFW/glfw3.h>
#include <glad/glad.h>

int main() {
    glfwInit();
    glfwWindowHint(GLFW_CONTEXT_VERSION_MAJOR, 3);
    glfwWindowHint(GLFW_CONTEXT_VERSION_MINOR, 3);
    glfwWindowHint(GLFW_OPENGL_PROFILE, GLFW_OPENGL_CORE_PROFILE);
    
    GLFWwindow* window = glfwCreateWindow(800, 600, "Hello", nullptr, nullptr);
    glfwMakeContextCurrent(window);
    gladLoadGLLoader((GLADloadproc)glfwGetProcAddress);
    
    while (!glfwWindowShouldClose(window)) {
        glClearColor(0.2f, 0.3f, 0.8f, 1.0f);
        glClear(GL_COLOR_BUFFER_BIT);
        
        // Render here...
        
        glfwSwapBuffers(window);
        glfwPollEvents();
    }
    
    glfwTerminate();
}
```

### Shaders
```glsl
// vertex.glsl
#version 330 core
layout(location = 0) in vec3 aPos;

uniform mat4 uMVP;

void main() {
    gl_Position = uMVP * vec4(aPos, 1.0);
}
```

```glsl
// fragment.glsl
#version 330 core
out vec4 FragColor;

void main() {
    FragColor = vec4(1.0, 0.5, 0.2, 1.0);
}
```

### Vertex buffer
```cpp
float vertices[] = {
   -0.5f, -0.5f, 0.0f,
    0.5f, -0.5f, 0.0f,
    0.0f,  0.5f, 0.0f
};

GLuint VBO, VAO;
glGenVertexArrays(1, &VAO);
glGenBuffers(1, &VBO);

glBindVertexArray(VAO);
glBindBuffer(GL_ARRAY_BUFFER, VBO);
glBufferData(GL_ARRAY_BUFFER, sizeof(vertices), vertices, GL_STATIC_DRAW);

glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, 3 * sizeof(float), (void*)0);
glEnableVertexAttribArray(0);
```

### Drawing
```cpp
glUseProgram(shaderProgram);
glBindVertexArray(VAO);
glDrawArrays(GL_TRIANGLES, 0, 3);
```

## 8. Vulkan Basics

Vulkan is the modern alternative. Powerful but verbose — "Hello triangle" is ~700 lines.

### High-level concepts
- **Instance** — the Vulkan loader entry point.
- **Physical device** — a GPU.
- **Device** — your logical handle to a physical device.
- **Queues** — submit work (graphics, compute, transfer).
- **Command buffers** — recorded sequences of commands.
- **Render pass** / **framebuffer** — what gets rendered into.
- **Pipeline** — fixed-function + shaders for a draw call.
- **Descriptor sets** — resources (textures, buffers) bound to shaders.
- **Synchronization** — semaphores, fences, barriers.

Vulkan makes you specify everything explicitly. Drivers do little for you. In exchange: predictable performance, multi-threaded command generation, less overhead.

### Why Vulkan
- Modern engine targets.
- Multi-platform: Windows, Linux, Android, Switch.
- Better performance ceiling than OpenGL.

### Why not Vulkan (for learning)
- Massive learning curve.
- "Hello triangle" is a multi-day project.
- Most rendering concepts can be learned in OpenGL first.

### Resources
- **vulkan-tutorial.com** — the standard.
- **vkguide.dev** — modern Vulkan with VMA, dynamic rendering.
- **Sascha Willems' Vulkan samples**.

For most game work, you'll go through an engine. Direct Vulkan is for engine developers and graphics researchers.

## 9. Memory and Performance for Games

### Pool allocators
Allocate a big block; hand out fixed-size slots:
```cpp
class PoolAllocator {
    char* memory;
    size_t slot_size;
    std::vector<void*> free_list;
public:
    void* allocate() {
        if (!free_list.empty()) {
            void* p = free_list.back();
            free_list.pop_back();
            return p;
        }
        // Grow...
    }
    void deallocate(void* p) { free_list.push_back(p); }
};
```

Constant-time alloc/free. Zero fragmentation. Cache-friendly.

### Arena / linear allocators
Single bump pointer:
```cpp
class Arena {
    char* memory;
    size_t offset = 0;
public:
    void* alloc(size_t size) {
        void* p = memory + offset;
        offset += size;
        return p;
    }
    void reset() { offset = 0; }    // free everything at once
};
```

Use case: per-frame temporary allocations. Reset at end of frame.

### Object pooling
Reuse expensive objects (particles, bullets, enemies):
```cpp
class BulletPool {
    std::vector<Bullet> bullets;
    std::vector<size_t> free_indices;
public:
    Bullet* acquire() { ... }
    void release(Bullet* b) { ... }
};
```

Avoids per-frame allocation/deallocation churn.

### Cache-friendly data layout
Hot data together:
```cpp
// Bad: pointer chasing
struct Entity {
    Position* position;
    Velocity* velocity;
    // ...
};
std::vector<Entity*> entities;

// Better: SoA (Structure of Arrays)
struct EntityData {
    std::vector<Position> positions;
    std::vector<Velocity> velocities;
};
```

The "vector of structs" vs "struct of vectors" question. For systems that process all entities' position-and-velocity, SoA wins.

### Avoid virtual calls in hot paths
Each virtual call: indirection, prevents inlining. Sometimes a tag + switch is faster:
```cpp
// Virtual:
for (Entity* e : entities) e->update();

// Tag-based:
for (Entity& e : entities) {
    switch (e.type) {
        case Tank: update_tank(e); break;
        case Tree: update_tree(e); break;
    }
}
```

ECS naturally avoids this — systems are direct, no virtual dispatch.

### Don't allocate in hot loops
```cpp
for (auto& enemy : enemies) {
    std::string log_msg = "enemy at " + std::to_string(enemy.x);    // allocates!
}
```

Pre-allocate, pool, reuse buffers.

### SIMD
Vectorized instructions process multiple values per instruction. Useful for math-heavy code:
```cpp
#include <immintrin.h>     // AVX intrinsics

__m256 a = _mm256_loadu_ps(&x[0]);    // load 8 floats
__m256 b = _mm256_loadu_ps(&y[0]);
__m256 c = _mm256_add_ps(a, b);
_mm256_storeu_ps(&result[0], c);       // 8 additions in one instruction
```

Or use libraries (Eigen, glm, xsimd) that wrap this. Many compilers auto-vectorize loops.

### Multi-threading
Game engines use thread pools / job systems. Frame work breaks into many small tasks distributed across cores.

Naïve threading (one thread per system) doesn't scale; job systems do.

## 10. Practical Starting Points

### Learning path
1. **Learn C++ well first.** Game-specific knowledge is on top of solid C++.
2. **Pick an engine.** Unity (C#) or Unreal (C++) — for a real first game, the engine handles 99% of the hard parts.
3. **Make small games.** Pong, Breakout, a simple platformer. Finish them.
4. **Study a graphics API.** OpenGL via learnopengl.com is the standard path.
5. **Read engine code.** Open-source engines (Godot, Bevy, custom engines on GitHub) teach a lot.

### For C++ game dev specifically
- Get comfortable with Unreal — it's the dominant skill for AAA hiring.
- Or build with raw graphics APIs + open-source libraries (SDL, GLFW, OpenGL/Vulkan, ImGui for debug UI).
- Learn the math: linear algebra (vectors, matrices, quaternions), basic physics.

### Recommended books
- **"Game Engine Architecture"** — Jason Gregory.
- **"Real-Time Rendering"** — Akenine-Möller et al.
- **"Physically Based Rendering"** — Pharr, Jakob, Humphreys.
- **"Game Programming Patterns"** — Robert Nystrom (free online).

### Communities
- **r/gameenginedevs** — engine development.
- **r/GraphicsProgramming**.
- **Graphics Programming Discord**.
- **handmadehero.org** — Casey Muratori's series on building everything from scratch.

### Reality check
- Building a competitive game engine from scratch is a career, not a weekend.
- Using Unreal/Unity is the realistic path to shipping a game.
- Custom engine work is for engine programmers, graphics programmers, and small teams with specific needs.

### C++ in non-AAA contexts
Even outside gaming, C++ graphics knowledge applies to:
- VR / AR.
- Simulation / scientific viz.
- CAD / 3D modeling tools.
- Embedded graphical displays.
- Browser engines.
